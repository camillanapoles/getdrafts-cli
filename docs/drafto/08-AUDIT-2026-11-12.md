## 1. O que é o projeto

| | |
|---|---|
| **Produto contratado** | **Drafto** — app **Android + Linux** com escopo e comportamento equivalentes ao **Get Drafts** (iOS/macOS, Agile Tortoise). |
| **Não é** | um cliente de Drafts, nem um bridge. É app próprio, com identidade (`drafto`, `drafto://`), que reutiliza *padrões* da família, não código proprietário. |
| **Repositório-base** | `camillanapoles/getdrafts-cli` — nasceu como CLI Go (macOS) que controla o Drafts.app via **AppleScript**; virou **monorepo Drafto** por decisão de continuidade (governança, releases, handoff no mesmo repo). |
| **Motor compartilhado** | `core/` (Go, platform-agnostic): modelo `Draft`, `Store`, `MemoryStore`, `SQLiteStore`, `ActionRunner`, template tags. |
| **Clientes** | `cmd/drafto` (CLI Linux/agent-facing) · `android/` (Compose + gomobile) · `cmd/drafts` (bridge macOS, herdado) |
| **Licença declarada** | MIT (governança §9). **Arquivo `LICENSE` não existe no repo** — ver D7. |

**Tese técnica do projeto:** o `core.Store` é a única fronteira. Todo cliente programa contra ele;
trocar backend (Memory → SQLite → sync) não pode tocar UI nem CLI. É isso que torna a base da CLI
reutilizável no Android sem CGO (`gomobile bind`).

## 2. Objetivo e definição de sucesso (fonte: `00-MANDATE.md` §2)

1. App Android **Drafto** com quick capture completo (inbox → tag → flag → archive/trash) local.
2. Cliente **Linux** com o mesmo comportamento do app móvel.
3. **Pareamento de features** documentado e rastreado (`02-FEATURE-PARITY.md`).
4. **Governança operante**: branches, SemVer, releases, handoff.
5. **Continuidade**: qualquer dev entende o estado a partir de docs + código.

## 6. Restrições do ambiente (afetam o plano, não são defeitos)

| Restrição | Medição | Implicação |
|---|---|---|
| Sem toolchain Go/Java no sandbox | `go: command not found`, `java: command not found` | **CI é a única fonte de verdade de build/teste** |
| Egress: só `github.com`, `codeload`, `api.github.com`, `npmjs`, `pypi` | `curl https://go.dev/dl/` → `000`; `https://proxy.golang.org/` → `000` | Não dá para instalar Go **nem** baixar módulos → não há "build local" possível aqui |
| Logs do Actions bloqueados por egress | lição registrada no handoff v0.3.0 | Diagnóstico só por **anotações + artefatos** (padronizar em SPEC-OPS-03) |
| Refspec do clone é estreito | `remote.origin.fetch` = `reverse/main` + branch próprio | `git log origin/reverse/v0.3.0…` falhava até `git fetch origin "+refs/heads/*:refs/remotes/origin/*"` — instrução obrigatória de início |

## 8. Veredito

O **núcleo está saudável e verificado por CI**: modelo, dois backends, actions e templates funcionam,
com testes. O que falta não é "mais features no core" — é **fechar a Phase 2** (integrar o que está
voando, expor actions no boundary com DTO estável, ligar UI ↔ engine) e **sincronizar a documentação**,
que hoje marca como pronto o que a CLI/UI não entregam (D1–D5) e omite riscos reais (D8).

Ordem que a auditoria recomenda: **OPS-01 (release v0.3.0) → AND-01 (boundary v2) → CORE-01/02
(conformidade + workspaces) → AND-02/03 (G3) → CLI-01 (paridade de superfície)**. Docs/ops correm em
paralelo com tudo (lane exclusiva de arquivos `.md`).
